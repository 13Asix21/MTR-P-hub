### 1.1 原始需求复述

雷爹的目标：**整个 Vault 在 wiki 化并传入 M 库之前，必须全部在面板界面上人工审核过**。即 connect-panel 要从「体检仪表盘」升级为「发布海关」——人工逐篇（或按条件批量）审核 Vault 内容，**审核通过的内容才是未来进入 M 库的候选**。面板本身不做发布，只产出可追溯、可导出的审核记录与放行清单，供后续阶段（阶段 3/4 的 Core 提案审批体系）消费。

### 1.3 真实 Vault 实测事实（写死为初始预期，不得编造）

| 指标 | 实测值 |
|---|---|
| Vault 根 | `C:/Users/Administrator/Nutstore/1/我的坚果云/Obsidian Vault` |
| managed root | 仅 `2-Permanent`（排除 `2-Permanent/Resources/MTR-P-System` 镜像与 `2-Permanent/Areas/AI-Assets/_templates`） |
| `.md` 文件总数 | 1832 |
| 可解析 | 1820 |
| `INVALID_YAML` 报错篇数 | 12（注意正确错误码写法为 `INVALID_YAML`，v1 文档中出现的 `INVALid YAML` 是笔误） |
| T 标签（`mtr/trial`） | 0 |
| R 标签（`mtr/rarely`） | 0 |
| unmanaged（无 MTR 标签） | 1820 |
| 双标签冲突 | 0 |

**本期审核队列全体 = 1832 篇（managed root 内全部扫描到的 `.md`），进度分母 = 1832。** 其中 1820 篇可解析（unmanaged，无 MTR 标签）+ 12 篇 `INVALID_YAML` 格式异常；按 Q6 裁决 12 篇异常篇同样进队列、标「格式异常」、可按原文预览、动作不限。**注意口径区别**：`unmanaged_notes=1820` 这个聚合数字**不含**异常 12 篇（解析失败的篇目无法判定 MTR 状态，故不进 unmanaged 计数），但审核队列是"全部扫描篇"，因此分母必须是 1832。

进度公式（唯一口径，全文一致）：

```
进度分母 = 扫描到的 .md 总数（实测 1832）
已审     = APPROVED + REJECTED + SKIPPED
未审     = 分母 − 已审
通过率   = APPROVED ÷ 已审（不是 ÷ 分母，避免未审期显示 0%）
STALE（内容已变更）单列，不并入已审，也不减少分母
```

上述计数是 2026-11-19 的实测快照，不得硬编码为永久值：Vault 变化后系统必须如实重新扫描（分母随实测变化），并把基于旧快照、内容已变的审核记录标记为 `STALE`（见 5.4 状态流转），而不是修改数字迎合基线。

## 2. 产品目标

**一句话目标**：把 managed root 下 1832 篇 Vault 笔记（1820 篇无 MTR 标签 + 12 篇格式异常），从「一盘散沙的文件夹」变成「一份按人、按篇、有理由、可回查的放行决策账本」——雷爹能在这个工作台里逐篇看过、逐篇拍板，并导出一份下游 Core 可消费的候选清单，同时不改变 Vault 与乐享的任何一个字节。

**成功标准**（三条正交、可验收）：

1. **可追溯**：每一次审核动作都留下 `(user_id, 相对路径, 动作, 理由, 内容 sha256, 时间)` 六要素记录；任意一条放行记录都能回答「谁在什么内容版本上、因为什么理由放行了它」。
2. **可导出**：任意时刻能把当前有效的放行集合导出为结构化文件（JSON 主 + CSV 副），格式稳定、字段自解释、含内容 hash 与 schema 版本，下游阶段 3/4 无需再读面板代码即可消费。
3. **可按人分化且可汇总**：每个用户档案各自维护独立审核进度，互不覆盖；同时提供一份 owner 只读全局汇总视图，让雷爹一眼看到「总共 1832 篇里，放行 x / 拒绝 y / 搁置 z / 未审 w」。

**不做成什么**：不是内容编辑器、不是质量评分器、不是发布按钮、不是 AI 分类器。

## 5. UI 设计稿（文字描述）

### 5.1 与现有卡片页的关系（推荐方案）

**推荐：新增一级 tab，同页切换，不做新页面路由。**

- 顶栏 `hero` 区域下方新增两个 tab：「四库状态」（默认，即现有卡片页）与「审核工作台」。
- 理由：v1 是单文件静态前端、无路由库。引入 hash 路由（`#/review`）成本不高但会改变现有「一屏看四库」的使用习惯；tab 切换保留现状、体量最小，且状态可在同一 JS 模块内共享用户选择。
- 用户选择器（`#user-select`）保持顶部唯一实例，两个 tab 共用同一 `current_user`；切换用户会同时刷新卡片页与审核工作台的用户维度数据。
- 硬要求：切到「审核工作台」不得自动触发扫描（沿用 v1「默认无自动轮询」），首次进入需显式点「扫描并载入待审清单」或复用卡片页最近一次扫描结果（若存在且未过期，显示「基于 HH:MM 的扫描结果」）。

### 5.2 页面结构（推荐：左列表 + 右详情双栏，窄屏退化为先列表后详情）

- 进度条区始终可见（sticky），因为「还要审多少」是雷爹最关心的信息。

### 5.3 关键交互

| 交互 | 行为 |
|---|---|
| 键盘 `J` / `K` | 下一篇 / 上一篇（在当前筛选结果内移动，不发请求，仅切换右栏详情） |
| 键盘 `A` / `R` / `S` | 通过 / 拒绝 / 跳过当前篇；`U` 撤销 |
| 焦点保护 | 焦点在理由输入框或搜索框时，`A/R/S/U/J/K` 均不触发动作 |
| 动作后 | 乐观更新列表徽标 → 保存成功后再前进到下一篇未审；保存失败则回滚徽标并显示封闭错误码对应的中文说明，**不静默前进** |
| 理由 | 默认折叠；点「拒绝」时自动展开并聚焦（仍非必填，见 Q2）；输入的草稿在切换篇目时按篇缓存（未保存不落库） |
| 批量确认 | 弹确认层，文案写明「将对 N 篇执行『通过』，其中含 M 篇格式异常」，需勾选确认框后才可点执行 |
| 导出 | 点击后先展示「将导出 N 篇（已排除 X 篇内容已变更）」预览，再确认生成；完成后给出文件名与「复制路径」 |
| 内容已变更 | 详情页顶部黄色提示条 + 「重新审核」按钮（把该篇动作重置为未审并记录一条 `STALE_RESET` 历史） |
| 扫描结果过期 | 顶栏显示扫描时间；超过会话即提示「清单来自 HH:MM 的扫描，建议重新扫描」，但不强制 |

### 5.4 状态流转图

```text
             ┌──────────────────────────────┐
             │          PENDING             │  ← 初始（扫描到的每一篇）
             │        （未审）              │
             └──────┬───────┬───────┬───────┘
              A     │  R    │  S    │  U
                    ▼       ▼       ▼  ▲
             ┌──────────┐ ┌────────┐ ┌────────┐
             │ APPROVED │ │REJECTED│ │SKIPPED │
             │  （通过）│ │（拒绝）│ │（跳过）│
             └────┬─────┘ └───┬────┘ └───┬────┘
                  │  U        │  U       │  U
                  └───────────┴──────────┴──────> PENDING

  任一已决状态 ──文件 sha256 变化──> STALE（内容已变更，自动打标）
  STALE ──「重新审核」──> PENDING（保留 STALE_RESET 历史）

  终态说明：
  · 初始状态对 **全部 1832 篇**成立，含 12 篇格式异常篇（`parse_status=INVALID_YAML`、`mtr_state=unknown`）；异常篇不限制动作。
  · APPROVED 是「进入导出集合」的唯一状态，但仅在 content_sha256 与当前文件一致时成立。
  · SKIPPED 是显式搁置，与 PENDING 语义不同：PENDING 是「还没轮到」，SKIPPED 是「看过了，先不决定」。
  · 已审 = APPROVED + REJECTED + SKIPPED；STALE 既不算已审也不减少分母 1832，需「重新审核」回到 PENDING 后才能重新计数。
  · 所有转移都是单向记录 + 可撤销；`history` 追加式，不覆盖。
  · 本状态机不产生任何 Vault 写入，也不产生 M 库发布动作。
```

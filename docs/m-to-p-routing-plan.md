### 1.2 关键缺口：M→P 路由并未真正跑通

现状是**两条独立的点对点通道**，不是路由：

```
M 库（乐享）  ──┐
                ├─ 各自独立，互不串联
P 库（GitHub）──┘
```

具体核实结果：

| 检查项 | 实际情况 |
| --- | --- |
| `routing/planner.py` 的 ReadPlan | 存在，但**只对内存 Fake 数据执行**（CLI 帮助明确写 `against in-memory Fake data only`） |
| `config/routing.yaml` 的 intent 规则 | 定义了 `project_context: P → M → T` 等五类意图，但**没有被真实数据源消费** |
| `adapters/lexiang.py`、`adapters/github.py` | 只有 `normalize()`，把**已有回执**转成 Canonical 事实；**自己不发请求** |
| 真正的网络调用 | 由 `execution/profile.py` 里写死的 MCP 工具名承载：`mcp__lexiang__call_tool`、`mcp__github__get_file_contents` 等，但需要**外部 Agent 按 Manifest 发起** |
| FastAPI / MCP Hub | `capability-matrix.md` 明确写 **disabled**，无服务端实现 |

**一句话结论**：路由的"规则"和"编译"有了，"适配器"有了，但**缺少把三者串起来、并真正发起 MCP 调用的执行宿主**。所以"M 库查询到 P 库"目前是**设计存在、链路未通**。

### 1.3 一个容易被忽略的前提

`routing.yaml` 里 `project_context` 的顺序是 **P → M → T**（先项目上下文，再知识库，最后试运行区），不是 M → P。
如果你要的是"从 M 库命中后去 P 库取项目资产"，那是一个**新的 intent 或新规则**，需要明确语义，不能直接复用现有配置。这一点必须先定，否则实现方向会偏。

## 二、要实现什么（先把语义钉死）

### 2.1 三种可能的"M→P 路由"，含义完全不同

| 方案 | 语义 | 典型场景 | 复杂度 |
| --- | --- | --- | --- |
| **A. 串联检索** | 先在 M 库搜到内容，再按内容里提到的项目名去 P 库取对应仓库文件 | 笔记里写"MTR-P-hub 的路由实现"，自动补上仓库里的源码片段 | 中 |
| **B. 引用补全** | M 库条目里带 GitHub 链接/仓库名，路由自动展开为 P 库文件内容 | 知识条目引用了某个 commit 或文件路径 | 低 |
| **C. 反向溯源** | 从 P 库的代码/ADR 出发，找到 M 库中解释它的知识条目 | 看代码想知道为什么这么设计 | 中 |

**建议先做 B**（引用补全）：规则确定、失败可控、能立刻体现"M→P"的价值，且不需要语义理解。A 和 C 依赖实体识别，建议放到第二阶段。

> ⚠️ 这一项需要你拍板。下面的计划按 **B 优先、A 次之** 编排，若你选 A 或 C，第一阶段的规则设计要改。

### 2.2 必须新增的组件

| 组件 | 作用 | 为什么现在没有 |
| --- | --- | --- |
| **路由执行宿主** | 接收一次查询，按 ReadPlan 依次发起 MCP 调用，汇总成结果 | 现在只能由外部 Agent 手工按 Manifest 调，没有常驻宿主 |
| **多跳结果合并器** | 把 M 的命中与 P 的文件内容按规则拼接，处理任一跳为空/失败 | 现有 `terminal.on_empty: return_empty` 只处理单跳终止 |
| **实体提取（仅 A/C 需要）** | 从 M 命中正文里识别仓库名 / 文件路径 | 未实现，且不能靠 LLM 猜（要可复核） |
| **MCP 客户端封装** | 统一乐享网关模式（`call_tool` 转发）与 GitHub 直连的差异 | 现在散落在 profile 常量里 |

### 2.3 明确不做的部分（避免范围膨胀）

- 不做写操作（GitHub 提交、乐享创建由现有传送链路单独负责，不进路由）
- 不做语义向量检索升级（M 库现有 `search` 足够起步）
- 不做多用户权限隔离（路由层与账号无关，鉴权在代理层）
- 不做真实 Vault 全量对拍（属独立专项）

## 三、分阶段计划

### 阶段 R1：路由骨架 + 引用补全（方案 B）

**目标**：给定一条 M 库命中，能自动展开其中的 GitHub 引用，取回文件内容。

| 步骤 | 产出 | 验收标准 |
| --- | --- | --- |
| R1.1 | `routing/rules.yaml` 新增 `m_to_p_reference` intent | 规则可被 planner 解析，单测覆盖顺序与终止条件 |
| R1.2 | `execution/mcp_client.py`：封装乐享网关调用与 GitHub 直连 | 两个真实端点各跑通一次只读调用 |
| R1.3 | `routing/host.py`：按 ReadPlan 顺序执行，逐跳记录回执 | 一条查询能产出完整的 跳→回执 链 |
| R1.4 | 引用解析器：从 M 正文提取 `owner/repo` 与文件路径 | 只接受正则可证的形态，**不猜**；无法解析则跳过该跳 |
| R1.5 | 结果合并与降级 | P 跳失败不影响 M 结果返回，且明确标注"P 未取到" |
| R1.6 | CLI `mtrp_hub route run --intent m_to_p_reference --query ...` | 真实跑通一次并留证据 |

**风险点**：乐享网关只暴露 `call_tool`，检索结果是 `content` 文本，需要解析 JSON；GitHub 文件路径必须先确认默认分支的 SHA 再取（沿用现有 `GITHUB_GET_COMMIT_TOOL` 链路）。

### 阶段 R2：串联检索（方案 A）+ 实体提取

**目标**：M 命中后按内容里的项目名，去 P 库检索相关文件。

| 步骤 | 产出 |
| --- | --- |
| R2.1 | 实体提取器：仓库名 / ADR 关键词，输出带原文位置的候选项 |
| R2.2 | P 库路径候选生成（按仓库目录结构推断，非盲搜） |
| R2.3 | 多命中合并与去重、相关性排序 |
| R2.4 | 真实样本对拍：同一查询，人工结果 vs 路由结果 |

### 阶段 R3：接入工作台（可选，取决于你是否要在界面里用）

**目标**：在审核工作台里加"检索"入口，直接调用路由宿主。

| 步骤 | 产出 |
| --- | --- |
| R3.1 | 代理新增 `/mtrp/route` 只读接口 |
| R3.2 | 工作台加检索页（输入查询 → 展示 M/P 结果） |
| R3.3 | 结果可跳转到原文（乐享条目链接 / GitHub 文件链接） |

### 阶段 R4：以本项目为唯一维护点

**目标**：把散落在各处的实现收拢到本仓库。

| 事项 | 现状 | 处理 |
| --- | --- | --- |
| 乐享凭据 | 分散在 `agent-bridge/.env` 与 `apps/mtrp-proxy/.env` | 统一到 `apps/mtrp-proxy/.env`（已 gitignore），`agent-bridge` 仅作参考 |
| Agent 网关配置 | 在 `agent-bridge/.env` | 同样收归本项目代理 |
| 代理代码 | 已在本仓库 `apps/mtrp-proxy/`、`tools/` | 已完成 |
| 主仓路由代码 | 已在本仓库 `src/mtrp_hub/` | 已完成，需补真实执行宿主 |
| 文档 | 本仓库 `docs/` + `apps/connect-panel/docs/` | 建立索引，见 §5 |

## 四、建议的下一步（按优先级）

1. **先定语义**：确认 M→P 是"引用补全"还是"串联检索"（§2.1）。这是唯一需要你决策的点。
2. **做 R1.2**：先写 MCP 客户端封装并各跑通一次真实调用。这一步不通，后面全是空转。
3. **做 R1.4**：引用解析器要保守，宁可少取也不要猜错——错取会把无关文件塞进结果，比没有更糟。
4. 其余按 R1 → R2 顺序推进，每阶段结束跑一次真实查询留证据。
